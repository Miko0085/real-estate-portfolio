## Structure

- `apps/*` — five isolated Astro static applications, each with eight required `docs/*.md` files.
- `packages/ui`, `typography`, `design-tokens`, `forms`, `analytics`, `seo`, `structured-data`, `utils` — shared source modules.
- `tests/` — deterministic unit tests without third-party test dependencies.
- `scripts/` — source structure checks and browser QA harness.

All portfolio data, prices, units, brochure content, floor plans and fictional names are **sample / illustrative**. Every lead form defaults to **demo mode**: validation works but **no submission is sent or retained** unless a real `PUBLIC_LEAD_ENDPOINT` is configured and a user consents.

## Cloudflare Pages monorepo setup

Create five independent Pages projects from the **same GitHub repository**. For each: use the **repository root** as the working directory and `npm ci && npm run build --workspace @estate/<app-name>` as the build command, with output `apps/<app-name>/dist`. `npm ci` requires the committed package-lock generated by `npm install`; until then use `npm install && npm run build --workspace ...`. Set `PUBLIC_SITE_URL` to the actual verified production origin per project, `PUBLIC_INDEX_SITE=true` only after reviewing content, and configure the endpoint only after the backend is live. Do not share domains/canonicals across sites.

The other apps are **not deployment-ready** until their implementation gates are completed.

## Submitting leads securely

Frontend form code is in `packages/forms` and `apps/dubai-offplan/src/scripts/lead-form.ts`. Use a same-origin Cloudflare Pages Function / Worker to validate fields, rate-limit abuse, check the honeypot, record consent, and authenticate against a private CRM token; **never expose CRM API keys client-side**. An external `PUBLIC_LEAD_ENDPOINT` must allow the deployed origin with appropriate CORS. Frontend validation is UX, not a security boundary. Without JavaScript, the POST fallback uses `/api/lead`, which is intentionally unimplemented until you deploy your first-party endpoint; it will not leak form details into the URL. The demo never stores data on a provider.

## Privacy & truthfulness

No fabricated testimonials, property transactions, licenses, commercial results or verified returns. No invented real agency contact details. First-party original SVG concept art and diagrams are labeled as fictional; no real-world property imagery is represented as original inventory. Demo indexing is disabled by default; set a verified site URL to enable indexing.

## GitHub publication

The repository archive is import-ready. Create an **empty** GitHub repo, `git init`, `git add .`, `git commit`, and `git remote add origin <your-new-repository-url>` then push. No existing user repository is silently changed.

## GitHub Pages portfolio deployment

The public static showcase is hosted at `https://miko0085.github.io/real-estate-portfolio/` after GitHub Pages is enabled. The portfolio root links to each independently built Astro app under its own subdirectory.

**One-time GitHub setting**: Repository → Settings → Pages → Build and deployment → Source **GitHub Actions**. The `.github/workflows/deploy-pages.yml` workflow then installs dependencies, checks code, builds all five apps with their GitHub Pages base paths, assembles a single `pages-dist` artifact, and deploys it.

The four non-Dubai apps are **explicitly unlaunched demo scaffolds**. The Dubai qualification form validates locally but does **not send leads** until a compliant HTTPS endpoint is configured. No server-side functions are provided by GitHub Pages. Public portfolio pages are noindexed intentionally while demo content remains fictional.

Local dry run:

```bash
npm install
GITHUB_PAGES=true npm run build:all
node scripts/assemble-pages.mjs
```

The standalone apps can still build for other static hosts with their normal root URLs when `GITHUB_PAGES` is unset.
